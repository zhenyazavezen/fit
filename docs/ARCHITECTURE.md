# Архитектура ZAVEZEN_FIT (запуск при $0/мес)

```
Телефон / браузер (PWA, Mini App)         Cloudflare (Free)
 ├─ статический сайт (GitHub Pages → затем Cloudflare Pages)
 ├─ localStorage = основное хранилище (работает офлайн)
 └─ sync.js ── HTTPS, Bearer-токен ──►  Worker «fit»  ──►  D1 «fit_db»
                                         ├─ /auth/telegram  (подпись initData)
                                         ├─ /auth/google    (Google ID token)
                                         ├─ /me, /link/*, /sync
                                         └─ лимиты частоты, CORS, валидация
```

## Принципы
- **Приложение работает без сервера.** Вход необязателен; без него всё хранится на устройстве, как раньше.
- **Сервер — копия и аккаунт.** Токен бота и ключи — только в secrets Worker; в репозитории, публичном JS и ZIP секретов нет.
- **Доверяем только проверенному.** `initData` проверяется по HMAC (ключ — токен бота) и сроку `auth_date` ≤ 24 ч; Google ID token — по подписи (JWKS), `iss`, `aud`, `exp`, `nonce`. `initDataUnsafe` на клиенте используется только для показа имени.
- **Сессия** — случайный токен 256 бит, в базе только SHA-256, срок 30 дней со скользящим продлением, выход и отвязка отзывают.
- **Единый аккаунт.** Таблица `identities` с `UNIQUE(provider, subject)` и `UNIQUE(account_id, provider)`: один вход принадлежит одному аккаунту, у аккаунта не бывает двух Telegram. Привязка второго способа — одноразовый код 8 символов (10 минут, ≤10 попыток за 10 минут, лимит на аккаунт), подтверждение владения обоими входами, предпросмотр и явное подтверждение объединения. По имени или почте аккаунты **не** объединяются. История не теряется (объединяется по id), избранное — объединение, настройки — более новые, Premium — максимальный срок.
- **Восстановление доступа.** Если привязаны оба способа — потеря одного не страшна. Если привязан один и он потерян, восстановить аккаунт нельзя (иначе это дыра в безопасности); поэтому приложение предлагает привязать второй способ.
- **Синхронизация.** Каждое изменение аккаунта получает номер ревизии (атомарно в одной транзакции `batch`). Клиент просит «изменения после ревизии N». Документы (settings, profile, favorites, programs): побеждает запись с более поздним временем клиента (время ограничено «сейчас + 5 минут»). Тренировки: идентификатор создаёт клиент → повторная отправка безопасна; удаление — надгробие. Офлайн: очередь на устройстве, отправка при появлении связи.
- **Изоляция данных.** Любой запрос к данным идёт только с `account_id` из сессии; клиент его не передаёт. Это проверено тестами.

## Таблицы D1 (`worker/migrations/0001_init.sql`)
accounts, identities, sessions, link_codes, user_docs, workout_sessions, rate_limits, audit_log. Платежей пока нет: в `accounts.premium_until` — готовое поле; таблицы счетов и платежей из `/home/claude/zavezen-db` (черновик на Telegram Stars) подключаются отдельной миграцией только по решению владельца.

## Защита
Проверка Origin (CORS по списку `ALLOWED_ORIGINS`), лимиты на вход (30 попыток за 10 минут на IP) и на коды привязки, ограничение размера (256 КБ), белые списки полей, единый формат ошибок без внутренних подробностей, `Cache-Control: no-store`. Чистка просроченных сессий/кодов выполняется попутно.

## Что не защищено (честно)
Каталог упражнений и программ лежит в публичном коде: блокировка Premium на клиенте — удобство, а не защита контента. Если Premium-контент понадобится прятать, его нужно отдавать с Worker только подписчикам (отдельная работа).
